# Existing-project research and build-vs-integrate decision

Research date: 2026-09-22. These are capabilities documented by the respective projects, not claims that VQS has run their complete integrations. Always pin and recheck the selected upstream version, contract, license and maintenance state before adding a dependency.

## Decision

**Build VQS as an independent orchestration and evidence product, not a renamed fork.** Existing projects solve valuable but *different* parts of the problem. Use first-party PBIR and Desktop tools for report validation/capture, integrate Fab Inspector as an optional policy engine, consider Draco 2 for chart suitability, and reuse the existing VQS source-linked review/repair work from PBIPDocumenter. Avoid copying an upstream codebase merely to own an already solved validator.

## Why not fork Fab Inspector immediately?

A direct fork would commit VQS to another project's .NET/rule-evaluation architecture and governance/Fabric scope while our existing source-bound evidence, Word page review, Pi reviewers and Python repair orchestration use different contracts. Instead, consume Fab Inspector findings through a **versioned adapter**, normalize them into common VQS findings, and run the quality/repair loop above that. Reevaluate a fork only if an upstream limitation cannot be addressed via a contribution, plugin or executable adapter, and document the maintenance and license costs first.

## Missing open-source capability to develop here

1. Reliable evidence that *the correct page, complete canvas, loaded data and exact source revision* were captured; distinguish image crop artifacts from genuine report clipping.
2. Joining PBIR, theme defaults (not merely explicit formatting), TMDL, effective filter context, data-distribution evidence and observed rendering into a visual-level fact model.
3. Testable design rules: distinct formatted ticks; axis label overlap budget; chart role/cardinality/task compatibility; visible Top-N/Other meaning; color consistency and contrast; table occupancy; page hierarchy. Report `unknown` when ticks, effective styles or data values cannot be obtained. Do **not** invent DAX values from pixels.
4. Separation of observed symptom, experimentally supported root cause, candidate repair, and independent re-rendered verification. Reject false-positive AI suggestions and repairs that hide categories or shorten tables.
5. Consistent handling of Power BI dashboards **and** paginated Word output, with PBIPDocumenter using VQS as a consumer rather than owning its release policy.

## Verification strategy before claiming differentiation

Test the same two unrelated PBIR projects against Fab Inspector and VQS and compare actionable overlap, missed defects, and false positives; measure label/tick/category fixtures with known values; run a saved-and-unsaved Desktop instance matrix; verify the repair changes improve actual output and maintain row counts; and run a DOCX with intentionally tiny text, stranded headings, split tables and stale report images. A model-generated positive review is **not** sufficient acceptance evidence.
